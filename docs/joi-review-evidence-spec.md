# Joi 总结与复查如何按路线图取证

2026-11-19 · 实施规格。审查基线为 `5880615`，当前实施范围见第 8 节。适用于主 Joi 的目标结果综合与 Wayfinder 复查，包括这两类回合的重试、恢复和收口。普通聊天、用户主动续写的上下文以及搭档接收 Work 的策略沿用各自的约定。[历史信息管理](historical-context-policy-spec.md) · [Pi 会话权属](pi-session-ownership-spec.md)

## 1. 审查结论

采用**从路线图定位、按验收要求取证、综合和复查共享已核实结果**的方案。完整性有两个可验证的含义：Joi 能找到本目标下每一份已保存且获准读取的成果，用户的每一项必选要求在结案时都有明确处置。任务多、报告长时，这两点仍然成立，无须逐字阅读每个搭档的全部输出。

| 基线中的行为 | 对方案的修订 |
|---|---|
| Harness 复查投递的正文带最近 8 份结果的摘要，每份最多 320 字符。读取 inbox 时，这类输入又走通用目标背景，查询最多 24 份结果的完整 `b.body`，在内存按单份 2 万、合计 12 万字符裁剪，再组装默认 2.4 万字符背景。生产查询先限制 8 行，复查正文无法据此得知真实遗漏数量。 | 优先改复查。投递、启动、纠正和恢复都从目标及版本重建同一份简短输入，在 SQLite 查询处就避开正文列。地图列出准确总数和下一页。保留复查已有的派发与结算身份。[复查投递](../src/main/infrastructure/persistence/sqlite-joi-harness-repository.ts) · [输入识别](../src/main/infrastructure/persistence/sqlite-joi-inbox-repository.ts) · [目标背景](../src/main/infrastructure/persistence/sqlite-joi-goal-context.ts) · [证据查询](../src/main/infrastructure/persistence/sqlite-workbench-context-repository.ts) |
| 正式综合已有版本化增量读取。首批最多 16 个变化结果，可以内联 320 字符预览、4,000 字符以内的交接，以及上次结论和结构化状态。两类回合没有相同的起始输入。 | 保留增量查询、版本和上一轮结论引用。将首批变化、交接及旧结论正文也放到显式读取入口。复查优先检查综合留下的覆盖和变化，避免再做一次综合。[综合快照](../src/main/infrastructure/persistence/sqlite-goal-result-synthesis.ts) · [变化页](../src/main/infrastructure/persistence/sqlite-goal-evidence-repository.ts) · [提示词组装](../src/main/application/joi/joi-continuation-prompt.ts) |
| Joi 可列 Work、读 brief、分页读结果和交接。现有目标详情能展示路线图，主 Joi 的工具集合缺少从地图定位某次 Work 执行的一体化读取入口。主会话历史也不能代表搭档在该 Work 中的执行记录。 | 复用地图、结果和安全执行投影，沿 `pathId → workId → runId → resultId / artifactRef` 导航。另提供尚未建图 Work 和无 Work 路径的入口。[地图查询](../src/main/infrastructure/persistence/sqlite-joi-goal-detail.ts) · [Joi 工具](../src/main/infrastructure/pi/joi-reasoning-tools.ts) · [结果分页](../src/main/application/work/work-result-service.ts) |
| 现有综合会校验所引结果、需求版本和适用范围；列出的 claim 可以获验，但未列的必选要求可能没有对应 claim。复查摘要还把缺失的验收记录显示成 `NOT_REQUIRED`。`PASSED` 的具体含义随验收项变化，例如 `BODY_PRESENT` 只检查非空。 | 分开保存“读到了什么”“实际检查了什么”“这些证据支持哪项要求”。覆盖全部必选要求才能自动宣布完成；已解决的旧失败仍可追溯。[综合状态](../src/main/infrastructure/persistence/sqlite-goal-synthesis-state.ts) · [Work 验收器](../src/main/infrastructure/workspace/workspace-work-verifier.ts) |

以上是源码行为。单凭界面的“正在总结”无法分摊数据库、模型、工具等待或重试的耗时。第 7 节给出可复现的测量方法。

## 2. 回合启动时给 Joi 什么

| 自动提供 | 具体内容 |
|---|---|
| 当前目标 | 本轮目的（综合交付或复查收口）、当前有效的目标、必选及可选要求与明确排除项，保留原意、需求 ID 和版本。用户最新纠正优先。短目标与有效要求可完整携带并去重。 |
| 当前工作台与工作位置 | 已绑定工作台的短描述，采用类似 skill 描述的粒度，只说明用途及适用范围；提供与本目标有关的工作区显示名、授权根引用、已知的任务相对目录及绑定状态。具体 Work 的执行根在选择该 Work 后读取。没有绑定时显式标明。目录文字不能授予访问权。 |
| 导航与身份 | 运行时签发的快照引用、路线图入口、当前层及路径/变化/未覆盖项计数、上次结论和覆盖记录的引用。自动输入使用固定种类的字段；各类清单均可分页。 |
| 既有运行约束 | 系统权限、工具契约、相关的 Joi 全局记忆继续按原策略处理。Joi 的 5,000、工作台的 20,000、搭档的 1,000 均是独立的历史字符压缩触发值。当前目标、导航和主动读取的证据独立计量。 |

以同目标的有效需求契约为准。缺少契约的旧目标先通过原始输入索引恢复有效目标；存在未处理补充时走现有需求整理流程。若当前要求本身超出可用窗口，用有序分页读完并保存需求处理水位，必选项及排除项全部可寻址。完成前校验已处理到最新来源版本，避免首尾裁剪吞掉中段纠正。[需求契约](../src/main/domain/work/goal-requirements.ts)

自动输入中的搭档结果正文、结果预览、交接内容、过程记录、产物内容、旧结论和旧会话回放均为 **0 字符**。工作台短描述使用独立来源，不能从某份搭档报告临时截取。这个约定覆盖首次调用、同一请求的备用背景档位、空工具回退和新执行段的种子；本回合主动取得的工具响应可以在 Pi 会话内继续使用。模型最后仍须向用户完整交付所要求的成果。

## 3. Joi 如何查到搭档的完整情况

下表定义读取契约，工具名可依现有端口合并。每次读取都由运行时从当前 Turn 解析工作台、目标与权限。模型只能选择该范围内的对象和页。

| 从哪里开始 | 可读内容及翻页规则 |
|---|---|
| 路线图 | 按层或指定需求查询路径、决策、雾区、相互引用、关联 Work、未建图 Work 及未关联要求。每类返回准确总数、稳定 ID、下一页。相同标题保留不同路径；同一 Work 多次出现可追溯，覆盖只计一次。非 Work 路径可用决策或用户排除项解释。地图缺失、正在补建或旧数据无需求关联时，仍可用目标 Work 和结果索引找到证据。 |
| 选中的 Work 与 Run | 读任务目标、brief、冻结的需求范围、验收项、依赖、搭档、尝试序列、当前权威尝试、执行及验收状态、结果与产物引用。按需单独展开旧失败、替换关系、等待/中断等已记录事实；如无可确认替换关系，显示未知。稳定引用可从当前结果反查路径和上游依赖。 |
| 结果、交接和过程 | 复用 `work_read_result` 的正文分页及 `work_read_evidence` 的变化、交接、结论和状态读取。选定结果可顺序读到末尾，保留中段、Unicode 和完整边界。过程页只提供归属于该 Run 的可公开执行事实，例如阶段、工具类别、状态、已有的检查结果及产物引用。Pi、原生和 A2A 分别声明实际记录的范围；区分未记录、源端已截断、已删除和暂不可用。原有私有对话、隐藏推理、工具原始参数、凭据与传输载荷沿用其权限边界。[结果服务](../src/main/application/work/work-result-service.ts) · [搭档执行投影](../src/main/infrastructure/persistence/sqlite-workbench-agent-repository.ts) |
| 产物与运行依据 | 从属于该结果的已登记 `artifactRef` 定位，按 MIME 和权限返回文本页、受支持的预览、摘要值或可信检查回执。区分结算时已保存的版本与当前目录中的文件；内容变化、删除、二进制无法预览或无匹配回执时标明限制。引用须同时满足目标归属和执行根权限。不能解析的任意路径、同目录另一目标的文件和外部 URL 均不能通过此工具扩大读取范围。需要运行验证时沿用已有搭档执行与授权流程。 |

第一次读取先看变化、未覆盖必选项及阻碍验收的冲突，再沿依赖找依据，随后才按时间补读。路线图和结果索引可按需请求同一批对象的有界元数据，避免 18 个搭档产生 18 次模型往返。若状态、交接及已有可信检查已经回答一个要求，可直接复用；关键内容在报告中段、有争议或用户明确要求全文审阅时，继续读取对应正文。标题、搜索命中和预览只用于定位。

建议将读接口收敛为三步：用快照和筛选条件列目录；用目录返回的稳定引用选择来源与游标；用返回的回执更新该项验收判断。每页给出来源版本、实际覆盖范围、是否到末尾和下一游标。证据内容按数据处理，报告中要求改目标、调用工具或扩大权限的文字不能改变当前任务。跨工作台或无权引用统一返回不可访问，避免泄露对象是否存在。

**示例。** 对一张有 19 条路径、1 次失败已解决的地图，若必选项是“客户端重启后继续执行”，Joi 先定位恢复实现与实测对应的路径，核对当前 Run，读与该版本匹配的重启测试结果。早期失败与替代结果相连且证据一致时保留其历史状态；替代 Work 只有“已修复”的自述时，记录缺少恢复实测。用户明确排除的功能在最终说明中保留其范围，无须因名称出现在旧路径上再次派发。

## 4. 快照、覆盖与结案

**快照。** 固定工作台、原始目标、结果版本、需求版本、有效地图版本、当前综合 owner 或显式恢复代次。索引、详情、正文游标及覆盖提交绑定相同范围和来源。遇到并发变化，按旧快照完成一致读取，或返回“快照已过期”及刷新入口；禁止一页里混入新版。提交时在事务内再校验当前版本、权威尝试、已吸收结果、用户门禁和活动执行。地图或权限可变且无法回放旧快照时采用明确失效。模型自己变更地图后同样刷新。

**覆盖的单位。** 采用有效契约中的 `requirementId`。一项含多个可独立失败的验收条件时，逐条记录来源和结论，沿用同一需求 ID；所有适用的必选条件都已满足才算覆盖。运行时从契约枚举必选项，初始状态为待核，模型遗漏一项会留下缺口。偏好和不影响验收的雾区记入说明。决定排除某项须引用其用户来源或有权限的范围决定，地图标记不能擅自豁免显式必选要求。

| 持久化内容 | 证明能力 |
|---|---|
| 读取回执 | 运行时记录快照、来源及不可变版本、Run、实际成功返回的页范围或检查回执 ID。失败、空页、仅列索引不能证明读过正文。工具重试幂等；现有用于经验学习的尽力记录不足以支撑结案。 |
| 每项覆盖 | 记录必选要求及验收条件、简短判断、所引回执、验收项类型、适用范围、状态（待核、满足、缺口、冲突）。用于必选验收的判断，其引用的每份结果都须有有效读回执。模型负责解释材料能支持什么，运行时核对来源、权威身份、覆盖范围与该条件要求的证据种类。阅读记录本身只能证明返回过指定区间。 |
| 上次综合的覆盖 | 冻结并随 outcome 保存，可由复查分页读取。相同内容和有效验收身份可复用。新增无关结果只复核增量；需求更正、当前尝试改变、验证撤销、产物内容变化或新冲突会使相关覆盖重新待核。跨需求版本复用必须重新确认执行时的适用范围和现行验收约束；无法证明时保留旧结论供追溯。 |

实现可扩展现有 `synthesisState`，由运行时关联独立存储的页回执和条件处置。读取回执落盘失败时不能用该次读取推进覆盖和游标。长任务按条件增量保存，启动及复查只读计数和引用；旧交接与整份覆盖表不进入新会话种子。证据已交给模型但尚未形成判断的情况可从检查点恢复。合并覆盖时使用当前版本校验和幂等键，避免并行页相互覆盖。

证据强度由验收条件决定。文字交付检查指定章节或结论时，可由 Joi 对选取的原文给出带来源的判断；文件存在性可由对应的 `FILE_EXISTS` 回执支持；“重启后恢复一次且没有重复派发”需要与构建版本、场景和断言匹配的测试或可观察运行事实。`BODY_PRESENT` 只证明有正文，`ARTIFACT_PRESENT` 只证明结果列有指定名称，`FILE_CONTAINS_EXACT` 只证明文件含指定文本。`NOT_REQUIRED` 与缺失验收分别保留，搭档自述、迟到或已替换的旧 Run 不升级为当前运行验证。缺少强证据的既有数据可另行核验；禁止从说明文本生成“测试通过”回执。

| 动作 | 必须满足 |
|---|---|
| 正式综合提交 `RESULT_SYNTHESIZED` | 所有必选项有当前有效覆盖，影响验收的冲突已有处置，保留既有完成 Work 与版本门禁。结构化工具和现有纯文本结算回退都在最终写入事务执行同一检查；纯文本只能复用已持久化的有效覆盖。 |
| Harness 完成及自动恢复收口 | 复用该综合的覆盖，核对地图、变化和遗留问题，并满足无进行中 Work、无未建图 Work、无开放路径等现有条件。工具主动清图、消费 review 时顺带清图、恢复 `AUTO_CLEAR` 和历史兼容收口使用相同的完成判定。若综合与覆盖均有效且没有变化，复查允许零次读取搭档正文。 |
| 有缺口 | 已有材料可查时优先补读；可安全安排的新验证走 `RESULT_CONTINUE` 和现有续跑额度；需要用户决策、权限或存在未决外部效果时走 `RESULT_BLOCKED` 或对应恢复门禁。读取故障按既有技术失败策略处理，不伪造用户问题。 |
| 用户接受、撤销和无 Work 目标 | 保留版本化 `ACCEPT_CURRENT → ACCEPTED_WITH_GAPS` 及缺口。取消/删除的地图清理沿用撤销语义。没有派发 Work 的直接回答沿用原流程。上述状态不产生“所有 Work 验收通过”的事实。 |

冲突可关联受影响的需求，并随结论保存处置说明与依据。未处置的必选验收冲突阻止结案，明确归属于可选要求或验收范围外的冲突继续保留。既有冲突缺少归属时，先核实其影响范围，或用当前已读、已验收且支持相应要求的结果处理。

## 5. 容量、调度和重启

- **按页取证，按轮限量。** 正文单页沿用最多 8,000 个 Unicode 码点；结果、交接、过程及产物等同轮读取共用证据预算。首版建议每段最多返回 32,000 码点的证据文本，实际可用量取此值与模型剩余容量（扣除工具定义、当前要求和输出余量）的较小值。预算覆盖批量和并行调用；元数据页也受序列化大小及调用次数约束。所有提供方请求，包括压缩请求，仍走现有容量检查。32,000 是可用合成测试调整的起步值。
- **把预算耗尽和任务失败分开。** 需要更多证据时保存已核条件、读取位置、未决项和下一引用，通过原调度器释放单槽并排队继续。新段只带有界检查点引用，由 Pi 管理段内压缩。重复读取同页算实际返回量，不能算作新进展；工具重试的同一请求不重复推进水位。相同快照连续两段没有新增覆盖、来源页或缺口处置时停下自动循环，沿用现有有界恢复与失败投影。有进展的长报告可以跨段读到末页。
- **保证恢复幂等。** 读取回执、覆盖检查点及续读调度使用稳定键，状态与必要 outbox 在同一事务落盘。启动校验后从首个未完成条件/游标恢复。已读回执只证明页面已返回；崩溃时若该页尚无判断，允许重读或从 Pi 的同次执行恢复。只读工具纳入协调器的安全重试分类，读取与新增验证派发分别记账。外部效果不确定时遵守现有门禁，其他可运行目标仍能获调度。
- **可观察性。** 使用现有进展投影区分排队、取证中、等待重试和已暂停，记录最近进展时间。诊断限于计数、规模、时长、安全原因类别；按阶段区分输入准备、工具 I/O、模型等待和重试退避。结果、路径、私有状态及工具正文不得进入诊断、SSE 或首页。

## 6. 实施顺序与旧数据

1. **先保证查得到。** 区分综合和复查输入种类，兼容旧输入 ID、owner 与恢复代次。复查继续走原消费语义；单独给它补 `result_revision` 会被当前代码识别为正式综合。补齐版本化导航、权威 Run、结果/产物分页和能力缺失状态，注册并测试主 Joi 的只读工具。验证覆盖原则所需的检查来源，功能实测如无可信适配器，先明确为证据缺口。
2. **再切换两类输入。** 从最容易重复加载的复查开始，随后切换正式综合。旧队列中已拼好的 review 正文只作历史记录，执行时重建最小输入；旧 Pi 会话在安全执行边界切段。移除这两类回合的自动预览与备用正文，保留普通继续流程。读取端口不可用时给出可恢复的内部错误；不回落到批量注入原文。
3. **最后启用完成判定。** 先让综合能够增量保存覆盖、续读和安全恢复，再在所有代表目标成功的事务入口启用第 4 节的判定。已收口的旧目标不批量重开；尚在运行且没有可靠覆盖的目标，在下一个安全回合从已存结果补核。显式重开只刷新受影响部分。最终交付和覆盖提交遵从已有 owner、事务及幂等约束，历史整理仍在有效结算后触发。

## 8. 首批实施范围

- 复查与综合从持久身份生成最小输入，并通过 `work_read_evidence(mode=roadmap)` 查找路径、未建图 Work、尝试、依赖、安全事件、产物引用和要求。正文、交接和结论由显式读取取得。SQLite 授权器回归在 1,500 万字符样本下禁止启动查询访问成果正文、摘要及交接字段。
- Migration 106 持久保存已读正文区间。正式综合核对必选需求、匹配验收和读回执，现有复查成功入口重新验证当前覆盖。仍活动的旧结论可排队补核一次，复用已完成 Work。
- 后续仍需完成按验收条件类型核验的可信实测回执、授权产物内容读取、跨读取工具的累计预算与自动续读调度，以及真实供应商与客户端负载测量。当前版本的 Run 活动提供安全元数据，恢复时可查询已读区间。

## 9. 收口与恢复优化

- 同版本补核失败会在首页与目标详情显示失败。用户直接继续可仅重试补核，保留此前结论和已完成 Work。正在执行或等待用户门禁的目标按既有状态推进。
- 启动需求以 Unicode 码点限制到 8,000，超限时优先保留完整的必选要求并给出分页入口。新用户输入仍按来源逐页处理，读完当前来源才推进处理水位。结论的旧数字分页兼容 UTF-16 游标。
- 回执区分不可访问、回合结束和证据 owner 变化。当前结论的分页绑定提交身份，同版本结论替换后须使用新游标。
