# 产品需求文档（PRD）

## 0. JOI-01 产品定义

joi 的产品定位是**支持多 Agent 调度、持续进化、多模型与多平台的 Super Agent**。产品只有一个唯一全局 joi。首页输入是用户管理所有人格、工程和工作的唯一入口；joi 通过 Pi 自动选择或创建工作台，维护持久化搭档列表，并决定拆分、串并行、派发、等待、改派和结果整合。用户无需管理多个工程、管线或任务才能开始。

目标验收摘要：输入在本地先持久化并返回 accepted；工作台正文严格隔离；原 Life 主 Agent 仅成为首选搭档；搭档更新先生成不可变 revision，再供新派发引用；所有副作用经过 outbox；模型源与凭据可恢复且不泄露。完整 AC-01 至 AC-30 见 `docs/10-requirements-traceability.md`。

既有 LIFE/EVENT/Wake 要求在迁移窗口内继续约束历史数据与旧只读 API，但不得创建第二个调度权威。

## 1. 产品定义

joi 是面向个人用户的 Super Agent，统一调度多个 Agent，连接不同模型来源，通过任务结果与反馈持续进化，并提供桌面、Web 与 Android 使用入口。本地常驻运行时负责持久化记忆、事件、目标和执行状态，让工作能够跨会话、跨天推进。

产品的核心任务是：**通过一个持续进化的 Super Agent，协调不同 Agent 与模型，让用户能够从多个平台持续、可靠地推进目标。**

## 2. 目标用户与核心任务

### 2.1 目标用户

- 在个人电脑上运行一个或多个 AI Agents 的个人用户。
- 愿意把电脑作为可信局域网中的常驻 Hub。
- 希望数字角色能持续陪伴、承担长期职责或推进跨天目标。
- 能从 AI Mana Agent 详情页取得 Agent Card URL 与 Bearer Token。

MVP 不面向组织管理员、多人团队或公网 SaaS 用户。

### 2.2 用户要完成的事

1. 连接一台或多台局域网 Agents，并确认它们可调用。
2. 创建数字生命，定义它是谁、在意什么、什么时候活动，以及使用哪些 Agents。
3. 通过对话、待办、闹钟和作息触发生命活动，而不是每次手动重建上下文。
4. 看见它正在做什么、为什么醒来、调用了谁、下一次何时醒来。
5. 在它需要输入、授权或关键决策时介入；其他时间允许它自行推进。
6. 在应用或 Agent 重启后继续，而不重复执行已经被远端接受的任务。

## 3. 产品目标

### 3.1 MVP 成功条件

- 一个新用户能在 10 分钟内完成首次设置、连接主 Agent、创建并启动第一个生命。
- 生命可以在没有新用户消息时由自身闹钟再次唤醒。
- 用户在主 Agent 工作期间发送消息不会销毁当前工作，消息会成为待处理事件。
- 生命能把任务异步委派给至少两个协作者，并在结果到达后继续主线。
- 关闭窗口后 Runtime 继续在托盘运行；应用重启后未消费事件与远端 Task 能恢复。
- A2A context 过期后，生命能用本地持久记忆建立新 context，而不是失去身份。
- 用户可以随时暂停一个生命或执行全局紧急停止。

### 3.2 设计原则

- **最少前置配置：** 默认值足以启动；高级调度和预算按需展开。
- **运行过程可解释：** 每次唤醒都能追溯触发事件、输入上下文、动作与结果。
- **自治不等于无边界：** 默认启用预算、安静时段和显式停止。
- **Agent 端权限有效：** Hub 不绕过 Agent 自己的 permission 或 auth-required。
- **失败不伪装成功：** 未确认远端接受、恢复或完成时，界面必须展示真实未知状态。

## 4. 核心用户旅程

### 4.1 首次启动

1. 本机桌面窗口打开首次设置页。
2. 用户设置单管理员口令；口令只保存为加盐派生值。
3. 用户选择是否开启局域网 Web，选择明确的 RFC1918 地址；默认端口 `43130`。
4. 用户粘贴主 Agent 的 Card URL 与 Bearer Token。
5. Hub 拉取 Card、验证 A2A 版本/transport/认证并执行无副作用 readiness。
6. 用户进入生命创建向导，填写名称、人格与主 Agent；其余使用推荐默认值。
7. 用户确认“出生”，Hub 写入 `system.birth` 事件并启动第一个 Wake。

### 4.2 日常对话与插话

1. 用户在生命时间线输入消息。
2. 消息先持久化为 `human.message`，UI 立即显示“已进入事件队列”。
3. 生命休眠时，事件触发 Wake；生命运行时，事件等待下一 Turn 或下一 Wake。
4. 主 Agent 通过 `express` 动作回复，消息与普通状态文本分开展示。
5. 用户能看到事件是否尚未读取、已进入哪个 Wake，以及回复由哪次动作产生。

### 4.3 自我唤醒

1. 主 Agent 返回 `alarm.schedule` 或 `sleep` 动作，声明下一次唤醒条件。
2. Hub 持久化闹钟并结束当前 Wake。
3. 到点后 Hub 写入 `alarm.fired`，通过预算和安静时段仲裁。
4. 主 Agent从意识残留、相关事务、记忆和事件自然接续。

### 4.4 协作者委派

1. 主 Agent 返回一个或多个 `delegate` 动作，只能选择生命配置中允许的协作者。
2. Hub 创建独立 Invocation，按 Endpoint 和全局并发限制调度。
3. 主 Agent不保持阻塞调用；当前 Wake 可以写残留并休眠。
4. 协作者完成、失败或请求输入时，Hub 写入相应事件。
5. 新事件再次唤醒主 Agent，由主 Agent整合、改派或向人求助。

### 4.5 人工介入

- `input-required` 被转换为待处理问题事件；用户回答必须绑定原 interaction。
- `auth-required` 始终要求用户处理，不允许主 Agent或协作者代答凭据。
- 用户可以暂停一个生命：保留队列，不开始新调用；已运行调用可选择等候或取消。
- 紧急停止会取消所有可取消调用、禁止调度并保持可诊断记录。

## 5. 功能需求

### 5.1 生命管理

| ID      | 需求                                                                                |
| ------- | ----------------------------------------------------------------------------------- |
| LIFE-01 | 创建生命时必须设置名称、人格摘要和主 Agent；头像、原则、角色和初始目标可选。        |
| LIFE-02 | 每个生命拥有独立事件、记忆、事务、作息、预算和 Agent context，不共享隐式状态。      |
| LIFE-03 | 用户可启动、暂停、恢复、归档和删除生命；删除前必须显示本地数据影响。                |
| LIFE-04 | 主 Agent变更必须先暂停生命，并生成有界交接摘要；不得迁移 Token 或远端原始 context。 |
| LIFE-05 | 生命列表显示当前状态、主 Agent、未处理事件、今日预算和下一次唤醒。                  |

### 5.2 Agent 连接

| ID       | 需求                                                                                  |
| -------- | ------------------------------------------------------------------------------------- |
| AGENT-01 | 用户通过完整 Card URL 与 Bearer Token 添加 Agent，不提供扫描或自动发现。              |
| AGENT-02 | Hub 必须验证 A2A `0.3.x`、JSON-RPC/HTTP+JSON transport、Card URL 与 Bearer Origin。   |
| AGENT-03 | Token 仅以 Electron `safeStorage` 加密后存储，不进入 renderer DTO、日志、导出或 URL。 |
| AGENT-04 | 主 Agent必须通过 joi readiness；未通过的标准 A2A Agent只能作为协作者。       |
| AGENT-05 | Card 的 Origin、协议、transport 或认证变化时，连接停用并等待用户重新确认。            |
| AGENT-06 | 用户可以测试连接、刷新 Card、轮换 Token、停用或删除连接。                             |
| AGENT-07 | 同一连接被多个生命使用时共享 429/503 冷却；breaker 不保存明文凭据且不丢弃事件。       |

### 5.3 事件与唤醒

| ID       | 需求                                                                                    |
| -------- | --------------------------------------------------------------------------------------- |
| EVENT-01 | 所有触发信号必须先写入持久事件表，禁止 UI 直接调用主 Agent。                            |
| EVENT-02 | 每个事件具有类型、来源、优先级、时间、payload 摘要、消费状态和关联实体。                |
| EVENT-03 | 同一生命最多一个主 Wake 运行；新事件不得销毁当前 Wake。                                 |
| EVENT-04 | 仲裁器必须执行优先级、去重、预算、安静时段、暂停和并发检查。                            |
| EVENT-05 | 一个 Wake 最多装配 50 个事件、总计 64 KiB；超出部分保持未消费。                         |
| EVENT-06 | 无可执行事件时生命必须回到 `SLEEPING`，不得空转调用模型。                               |
| EVENT-07 | 可自动唤醒的事件必须注册 schema、优先级、合并、上下文和重试策略；未知类型不得自动运行。 |
| EVENT-08 | 运行中到达的事件只发轻量信号；Agent 真正读取前不得复制正文或提前消费。                  |
| EVENT-09 | Wake 存活由进程标记、Turn 心跳或启动宽限证明，不得使用普通业务更新时间。                |

### 5.4 记忆与连续性

| ID        | 需求                                                                         |
| --------- | ---------------------------------------------------------------------------- |
| MEMORY-01 | 原始事件和动作形成不可变活动记录；修改使用新事件，不覆盖历史。               |
| MEMORY-02 | 每个成功或部分成功 Wake 保存意识残留、关注事务和建议下一步。                 |
| MEMORY-03 | 情景记忆关联事件、事务、时间与实体；语义记忆保存稳定事实、偏好、规则和教训。 |
| MEMORY-04 | 召回使用 SQLite FTS5、实体标签、时间和事务关系，不依赖外部向量数据库。       |
| MEMORY-05 | 默认每晚 `03:00` 生成记忆整理事件；整理结果仍通过结构化动作提交。            |
| MEMORY-06 | A2A context 重建时只注入有界交接包，不向远端 dump 全部历史。                 |
| MEMORY-07 | 有来源支持的概念卡优先于碎片召回；摘要是可重建投影，不静默删除原始活动。     |

### 5.5 作息、待办、闹钟与预算

| ID        | 需求                                                                                     |
| --------- | ---------------------------------------------------------------------------------------- |
| RHYTHM-01 | 默认提供早间计划 `08:00`、晚间复盘 `21:00`、记忆整理 `03:00` 三个可编辑作息。            |
| RHYTHM-02 | 用户和主 Agent都可创建一次性或重复闹钟；所有时间以生命时区解释。                         |
| RHYTHM-03 | 待办具有标题、状态、截止时间、事务和负责人；逾期产生事件而非直接调用 Agent。             |
| RHYTHM-04 | 默认安静时段 `23:00–07:00`；期间允许内部维护和紧急事件，但非紧急表达延迟到安静时段结束。 |
| RHYTHM-05 | 默认每日 24 次自主唤醒、100 次 A2A 调用、3 次空闲探索；用户可按生命调整。                |
| RHYTHM-06 | 用户消息、auth 和恢复事件不消耗自主唤醒额度，但仍消耗 A2A 调用额度。                     |
| RHYTHM-07 | 达到额度后生命进入 `BUDGET_PAUSED`，用户可追加额度或等待次日重置。                       |
| RHYTHM-08 | Alarm 到 Event 的 occurrence 必须原子且幂等；投递失败时 Alarm 保持可重试。               |

### 5.6 表达、Artifact 与协作

| ID        | 需求                                                                        |
| --------- | --------------------------------------------------------------------------- |
| ACTION-01 | 主 Agent只能通过已定义动作改变生命状态；自然语言正文不能直接写数据库。      |
| ACTION-02 | `express` 是独立消息动作，协议状态“完成”不得混入正式回复。                  |
| ACTION-03 | 协作者只能接收自己的任务、必要上下文和明确附件，不读取完整生命记忆。        |
| ACTION-04 | 协作者结果、失败、input/auth 和 Artifact 必须先成为事件，再由主 Agent处理。 |
| ACTION-05 | Artifact 下载、预览和转发遵循大小、MIME、路径与授权检查。                   |
| ACTION-06 | 不提供通用的每动作人工审批；Agent 端 permission 与 auth-required 保持有效。 |

### 5.7 Web 控制面

| ID     | 需求                                                                        |
| ------ | --------------------------------------------------------------------------- |
| WEB-01 | 桌面内嵌 UI 与局域网浏览器使用同一套 React 应用和 `/api/v1`。               |
| WEB-02 | LAN 用户使用管理员口令登录；桌面内嵌 UI 通过一次性本地 bootstrap 建立会话。 |
| WEB-03 | 活动、状态和调用进度通过 SSE 增量更新，断线后可用游标恢复。                 |
| WEB-04 | 每个危险操作都必须有清晰后果；不得增加无必要的多步审批。                    |
| WEB-05 | UI 必须区分用户消息、生命表达、系统状态、Agent 结果和错误。                 |
| WEB-06 | 用户可在桌面设置中启用 Android 原生远程，扫码后在竖屏 App 查看 joi 首页任务卡并提交文字；同网优先直连、公网自动回退 iroh 中继；二维码十分钟、一次有效，允许多手机独立绑定，业务内容端到端加密。 |

## 6. 非功能要求

- **持久性：** 事件、动作、本地状态和 outbox 在事务提交后才允许外部副作用。
- **恢复性：** 崩溃恢复不得盲目重发已经可能被 Agent 接收的消息。
- **性能：** 10 万条活动记录下，生命时间线首屏在本机 1 秒内可交互；历史按游标分页。
- **资源：** 空闲 Runtime 不持续调用 Agent；SQLite 使用 WAL，后台整理必须可中断。
- **可观察：** Wake、Turn、Injection、Invocation、FlowEvent 和 action 使用稳定 id 与因果引用，可重建调用输入和动作结局。
- **隐私：** 日志不记录 Token、完整人格、完整消息、记忆正文或原始 A2A payload。
- **可移植：** 生命周期数据可导出为版本化备份；密钥只在目标机器重新输入或重新配对。

## 7. 非目标

- 多账户、角色权限和多人共同控制一个生命。
- 云端托管、云同步和通用公网管理访问；ADR 0013 的受限 Android 原生远程入口除外。
- 飞书、微信或其他第三方消息通道。
- Agent 自动发现、广播、Agent 配对和 Agent 市场；浏览器设备的显式二维码绑定不属于 Agent 配对。
- 数字生命自行修改 Hub 源码、安装技能或发布版本。
- 向量数据库、知识图谱服务和独立模型 API Key 管理。
- 完整项目/KPI 管理、财务交易执行或高风险现实世界自动化。

## 8. 产品验收定义

MVP 只有在 [路线图与验收](07-roadmap-and-acceptance.md) 中的生命周期、A2A、恢复、记忆、Web 和桌面门禁全部通过后，才能从“实验性”改为“可用”。文档阶段不把任何需求标为已实现。
