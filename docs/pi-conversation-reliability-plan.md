# 对话搭档稳定性与可靠性修复方案

日期：2026-11-13。状态：已实施，本地质量门禁通过。本文保留修复前的证据边界和设计依据，并以 REL-01–16 约束实现验收。

实施基线为主分支 `3ad74b7`，Pi 三个运行时包均为 `1.5.2`。主干整合基线为 `40a62b2`，同时保留对话重命名、回复实时推送、摘要优化、耗时观测和界面变更。开发和验证在 `20261112-bugfix` 工作树完成，测试使用临时数据和凭据替身。

## 实施记录

- P0：连接提示与执行失败分离；GET 超时、取消、退避、认证停止和选择代次门禁；安全失败事实与部分产物持久化。
- P1a：SDK 版本化头、条目、父身份、叶节点及 context edit 增量落盘；原生引擎保留 canonical 源；未知工具效果通过 context edit 转为明确参考事实。
- P1b：SDK 单层有界模型恢复，provider 重试为零；重试次数跨阶段保留；工具及下一模型请求前排空必要写入；SDK 最终结算与清理完成后提交终态。
- P1c：模型空闲与重试等待分离；取消覆盖 SDK 退避，SDK abort 最多等待五秒；worker start/stop/close 控制请求有明确期限。保留原有摘要单飞、冻结覆盖、容量校验、取消及退避策略。
- P2 评估：异步 provider 永不响应取消时，另一对话仍可完成，原会话在期限后收敛且迟到事件不能落盘或执行工具。本轮不拆分每对话 worker；同步阻塞隔离和真实供应商表现仍需独立评估。

## 问题与证据边界

用户希望搭档在长对话、模型瞬断、摘要失败、切换页面和停止操作时保持连续性，并能知道当前是在执行、恢复、等待还是已经失败。

修复前已确认的事实：

1. 当前对话通过 `AgentSession.prompt()` 开始，但模型失败后的恢复会删除 Agent 内存中的失败消息，再直接调用底层 `Agent.continue()`；SDK 自动重试关闭。
2. 真实 Pi 1.5.2 和当前会话工厂的内存探针中，手工续接后 Agent 中失败消息数为 0，`SessionManager` 投影中为 1，且没有 context edit。再发送一轮后差异仍存在。这证明两个运行态表示不一致，尚未证明它就是截图红框的触发原因。
3. 同一工厂只在探针中启用 SDK 重试后，Agent 和 SessionManager 投影中的失败数均为 0，原始条目仍保留一次失败，并新增一次 context edit。事件依次包含 `agent_end(willRetry=true)`、重试开始/结束和最终 `agent_settled`。两个探针均使用合成消息、内存会话和凭据替身，没有真实模型请求。
4. 当前私有会话保存消息数组、宿主摘要检查点和摘要退避；没有保存 SDK 条目的身份、父子关系和 context edit。会话一致性修复需要覆盖持久化与恢复。
5. 对话服务会把非 DomainError 的包装错误折成 `conversation_execution_failed`。底层已有的安全原因码未完整传递到界面。
6. 前端轮询失败设置全局提示，成功刷新没有清除对应提示。隔离测试中，空 HTTP 错误后能收到新内容，横幅仍保留；期望恢复后清除的断言失败。真实 Vite 的隔离代理遇到上游连接重置时返回空的 HTTP 502/text/plain，可触发该兜底。
7. 运行时已具备对话私有会话、outbox、事件游标、单对话活动轮次互斥、子代理取消和后台摘要。这些能力应继续复用。

既有终端捕获覆盖到 14:20，其中一轮完成 17 次工具调用：14:16:23 模型失败后恢复，14:18:41 再次失败，最终安全原因码为 `timeout`。当前 dev 在 14:41 启动；该日志不能直接证明新实例中截图那次 HTTP 失败的原因。方案分别修复已复现缺陷并补齐观测，不把未确认归因写成结论。

## 用户可见的目标行为

1. 模型瞬断时，当前轮次显示恢复状态；恢复成功后继续已有工具结果，保留原始失败事实。
2. 界面暂时连不上后端时，显示连接状态并继续恢复读取。服务端任务状态由服务端事实决定。
3. 恢复读取成功后，对应连接提示消失；发送、删除或工具执行失败仍保留自己的提示。
4. 重试耗尽时，展示可理解的失败类别和已有产物，提供后续处理入口。
5. 用户停止时，退避等待、模型、摘要和子代理都接收取消；停止后的迟到事件不能恢复成运行中。
6. 摘要失败时，保留可用检查点与原始历史，在容量允许时继续主请求。
7. 关闭、重启或 worker 中断后，可读到最后持久化事实；效果未知的工具不会被自动重放。
8. 在桌面、LAN 与远程界面重连后，同一对话能补齐进度和终态。

## 实施决策

### 第一批：准确表达失败和界面恢复，优先级 P0

**保留安全失败事实。** 复用现有搭档失败分类，在引擎、实例管理、对话服务、存储和共享 DTO 之间传递有界原因码。至少区分模型超时、网络错误、限流、认证/配置、上下文容量、工具失败、持久化失败和进程中断。未知错误使用固定类别。

公开投影只携带安全原因码、失败阶段、恢复次数、下一次恢复时间和是否需要检查已执行效果。原始异常、HTTP 响应正文、消息正文、模型 payload、路径和凭据不进入诊断或错误 DTO；私有会话和工具记录继续遵守各自的存储边界。

**拆分任务状态和连接状态。** 保持既有 turn status；运行中的恢复以附加状态表达。HTTP 读取错误只改变连接状态；最终执行失败以持久化终态表达。认证失败停止自动恢复读取并显示认证要求。

**让轮询能收敛。** GET 加入取消和超时。对话切换、新建草稿、组件卸载及请求被替代时取消旧读取，并以会话 ID、选择代次和请求序列拒绝迟到结果。成功只清除本读取恢复周期的连接提示。连接失败采用有上限的退避，成功后恢复正常活跃轮询；游标只在相应数据已被接受后推进。

宿主策略：读取超时 10 秒，失败间隔 1/2/4/8 秒后封顶 15 秒，并加 0–10% 抖动；成功后恢复正常轮询：实时流连接时为 700ms，实时流不可用或断开时为 100ms。已接受的实时更新也会清除本会话的连接提示；更早的读取结果或异常不会覆盖新推送。权限拒绝会停止自动读取并关闭实时订阅。假时钟验证取消与时序。发送和其他写请求继续使用已有幂等身份；读取恢复不提交消息、不启动执行。自动恢复提示只用于正在重读的进度连接，普通写入失败不声称会自动重发。

**可追踪但不泄露内容。** HTTP 故障通过状态码、安全 ApiError 分类和连接提示识别；Pi 恢复通过安全状态投影、既有耗时诊断和稳定 turn/call 身份追踪。非 JSON 的 502 等响应映射成传输类别。后续若扩展 HTTP 诊断，只记录方法、固定路由模板、状态码、原因码、关联 ID、耗时和状态转换；实际资源路径、游标内容、请求头和响应正文不进入诊断。

### 第二批：统一正常对话的会话与恢复，优先级 P1

**采用一个会话适配边界。** 正常 Pi 对话的提示、模型级恢复、取消、事件和最终结算由 AgentSession 管理。移除这一路径中手工删改 Agent 消息再直接调用底层 continue 的恢复方式。SDK 类型和原始事件留在基础设施；应用层继续通过端口获得安全执行事实。

**SDK 管理重试，Joi 管理执行约束。** 对正常对话启用明确配置的 SDK agent-level 重试，provider-level 次数为 0，并移除同一路径的宿主追加一次续接。初始最多 3 次恢复尝试，基准退避 2 秒，单次等待上限 60 秒；只针对固定源与模型 revision 的可恢复模型错误。实际等待计算和服务端延迟支持以 1.5.2 已安装 API 为准，不凭文档推定未暴露的选项。

用户取消、认证/配置错误、工具错误和存储错误各走自己的收敛路径。上下文超限交由现有压缩及容量校验处理。模型重试保持当前 turn、模型 pin、工具调用身份和权限；不创建新 Work，不再次投递整轮 outbox。

对话附加状态持久化恢复周期和已用次数，覆盖 READ/WRITE 会话重建；SDK 的私有计数器不作为持久化接口。主请求成功且结果已保存后结束本恢复周期。子代理使用相同模型调用策略，并受原有父子生命周期约束。

**保存可重建的 SDK 条目。** 私有存储增加版本化条目日志，按稳定条目 ID、父条目 ID 和条目类别增量追加，保存选中叶节点及 context edit。其载荷在端口中保持不透明，SQLite adapter 与 Pi adapter 负责序列化和转换。使用 SDK 公开的内存会话构造及上下文投影接口重建，不访问私有字段。

实施时新增递增 SQLite 迁移，复用现有对话所有权及事务；原私有消息保留为旧会话导入来源。旧记录无损导入可用历史，明确保留原有 missing-history 语义。迁移不创建执行意图。新会话避免在每次保存时把全量历史重复写入 JSON 元数据。

原始条目保存完整事实；模型上下文应用 SDK 的省略编辑和 Joi 的摘要投影；界面继续使用安全 DTO。宿主摘要索引必须有稳定源条目身份或明确映射，不能把 SDK 条目下标当成已有消息下标使用。

**用最终结算作为终态前提。** 订阅 SDK 会话事件，以 `agent_settled` 或受支持的等待空闲接口确认模型恢复和内部队列已结束，再等待子代理、摘要清理、私有条目及公开投影写入完成，最后提交 turn 终态。最终仍要检查可用正文、失败事实和原有完成条件。

**先记录效果，再允许恢复。** 工具开始前保存稳定调用意图，工具结束后保存完成事实；恢复进入下一次模型请求前排空必要写入。记录不完整或保存失败时进入效果未知/持久化失败路径，停止自动动作重放。沿用现有私有会话及工具回调接缝，不给业务层引入 SDK 或 SQL。

这批工作需要修订 ADR 0033 中“SDK retry disabled”的正常对话决策。唯一 Joi 的自主调度、模型源选择、工具权限、outbox 和共享摘要仍由现有宿主模块负责；SDK 自动摘要继续关闭。本方案不把自主 Joi 的全部执行路径一并迁移。

### 第三批：摘要、取消与进程故障收敛，优先级 P1/P2

**保留已有摘要策略并补故障联动。** 继续使用单会话单飞、冻结覆盖、净节省校验、完整响应校验、30/120/300 秒退避及最多 5 秒硬容量等待。摘要状态独立于连接状态和 turn 终态。摘要失败保留旧检查点；共享同源请求资源时主请求优先，摘要遵守原有预算，不新增全局业务调度器或活动对话数量限制。

**分别约束各类等待。** 网络连接、流空闲、工具执行、SDK 重试、子代理收尾和数据落盘采用各自的期限与取消信号。运行中的真实模型/工具进度与恢复等待可区分；普通心跳不能无限刷新业务进展判定。长任务继续受既有预算和有意义进度约束。

**停止先取消，再收尾。** 保持控制权直到模型、重试等待、摘要和子代理结算，排空持久化后释放同对话活动槽位。收尾超过期限时保留可读的中断/未知事实。会话代次、当前 turn 和所有权校验阻止迟到回调写入下一轮。

**进程恢复只恢复可证明安全的内容。** worker 退出拒绝未完成控制请求；每个 worker 的独立 RPC 及递增请求身份隔离旧回复，关闭会清理订阅。启动后恢复界面和未开始的 durable intent；已开始执行的轮次显示中断/未知。本轮不自动重启 worker；启动等待最多 60 秒，紧急停止和关闭控制请求最多 15 秒，随后关闭会终止自有 worker，避免自动崩溃循环。

每对话独立 worker 是参考项目的隔离手段，列为 P2 评估项。只有故障注入证明单个 Pi 卡死会拖住其他对话、且现有取消不能隔离时才实施；Joi 当前的单调度权威和数据库所有权需要独立设计，不能直接复制桌面项目的 worker pool。

## 交付顺序与回退

1. **P0：错误事实与连接恢复。** 先让失败可见、提示能收敛；独立发布和验证。
2. **P1a：SDK 条目持久化及单一会话边界。** 先锁定导入、恢复、投影、取消和落盘一致性，保持恢复策略可控。
3. **P1b：SDK 模型重试与最终结算。** 在 P1a 上启用单层有界恢复，移除正常对话旧续接路径，完成工具不重放和失败原因回归。
4. **P1c/P2：故障联动与隔离评估。** 完成摘要资源、取消期限、进程故障和跨端重连回归，再按故障证据决定是否拆分 worker。

每批可独立审阅和回退。条目格式需要版本与兼容读取；回退恢复策略时使用保留新格式的只读/手动恢复模式，不能让旧运行时误读并执行新记录。自动模型恢复可关闭，但仍保留单一会话边界与完整源事实。

成功指标来自故障注入：恢复成功率、已完成调用被重放次数为 0、终态原因完整率、连接恢复后残留提示数为 0、取消收敛时间及持久化往返一致性。稳定调用身份用于识别同一次调用；不同身份的新业务动作仍接受原有权限及效果校验。真实供应商表现需另行复测；本次探针不能证明生产延迟或成功率已经改善。
