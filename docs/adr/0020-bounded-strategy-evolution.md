# ADR 0020：分层作用域的受限策略进化

- 状态：Accepted
- 日期：2026-09-22
- 关联：ADR 0002、0010；AC-EVO-01 至 AC-EVO-08

## 当前决策：2026-10-23 真实任务事实驱动的方法学习

本节取代下文历史决策中关于触发门槛、策略模块、预算和晋升的旧口径。策略合同版本为 `2`，评测器标识为 `joi-method-learning-v1`；它们分别标识声明式方法格式和评测规则，不是同一个版本号。旧批次、成本、暂停选择和目标绑定继续保留，升级不重放历史任务，也不自动恢复已暂停的工作台。

### 事实、方法与隔离

从已收敛目标的当前需求版本、结果版本、权威验收、需求覆盖、引用归属、依赖和重复读取事实生成不可变结构案例。案例 ID 同时包含目标、双版本、缺陷及权威事实快照摘要；同一双版本内验收或覆盖变化也产生新案例，仅观察时间改变不产生新案例。目标及已知同源近重复案例使用稳定来源组划分开发/封存集，同一来源组不能跨集合或充当多个独立封存样本；缺少可靠同源信息时仅回退原目标身份，不猜测内容相似性。输入适用条件只使用显式需求有无及数量桶（≤10、≤100、>100），不能用成功、失败、覆盖率或引用错误等处理后结果匹配生产对照。

取消、环境/执行失败、缺少有效双版本及无任何客观验收的观察不进入学习案例。正例同时要求权威完成状态、客观检查通过、完整已声明需求覆盖及无机械缺陷；未完成且只有冗余读取也不能成为正例。机械可判定的失败或缺口可以生成继续验证案例；需要用户决定的生产 `wait` 判定尚无完整来源合同，不能从主观状态补造。原文及私有来源保存在所属工作台，跨台评测只使用结构计数与别名；模型自评不能产生独立成功标签。

上下文、规划、结项三个模块各选择最多三个注册操作，每个候选只改变一个模块。运行时只解释固定模板，不执行生成的代码、任意工具说明或自由指令；用户要求、权限、验收器和副作用门禁始终优先。工作台有效覆盖优先于全局基线，新目标在需求 READY 后固定完整策略与模型来源版本。全局候选的最终评测数据必须至少来自两个工作台。

### 生产形状的决策段重放

首版回放权威事实对应的上下文取证、规划及结项决策段，不重新执行真实长任务。`read_evidence` 读取结构记录，`finish` 由固定判定器评分；依赖问题另须提交 `work_plan`，使用生产工作计划的字段合同和领域 DAG/执行权限约束，验证隔离别名的前置依赖、显式验收及只读能力。缺计划、跨案例引用、自依赖、环及额外执行能力均不能通过。原安全题库不额外要求计划。重复读取会增加实际模型调用成本，不改变既有权威验收事实。

模型只接触开发案例和其执行轨迹。独立评测必须包括三十个不同固定安全场景，以及至少五个独立来源组的生产派生封存案例；每个场景/案例的基线和候选各执行三次。质量改善对象须在基线三次中至少两次重现失败；纯效率对象须有客观冗余读取信号及保持成功的对照。安全题库只承担回归门禁，不进入生产收益分母。以上只能证明结构决策行为，不能证明真实文件处理、网络、Shell、压缩、长任务执行或用户主观质量改善。

### 调度、成本与收益

所有参与工作台共享默认每日 150 次后台模型调用，UTC 日重置；工作台旧预算保留为兼容子上限。全局同时最多一个未完成实验；自动候选每日最多一个，显式立即评测仍受共享预算及单槽位约束。每次调用前原子保存稳定调用标识、预算预留和检查点，通过现有 outbox 审计；协议检查、提案、评测、失败及中断均计费，未知用量不退款、不记为零。前台有效待办优先，已取消父目标的遗留输入不能永久阻挡空闲。

批量评测前先完成连续三个逐次工具协议检查；连续两次无效响应暂停当前实验及全局后台，不轮换工作台重复付费失败。显式恢复必须重新预检；相同 pin 的已完成试验只能用于原策略，切换模型/来源须重新固定版本并失效不兼容试验，不能将旧候选结果移植到新候选。中断保留账目和有效基线缓存，协议失败不消费缺陷证据。缓存键包含来源、模型、工具、评测器、策略、案例及尝试编号。

封存判定要求零硬违规、每个场景成功次数不下降，并满足一条收益通道：质量成功率提高至少五个百分点，调用及已知配对 Token 增幅均不超过 10%；或质量不降，调用/完整已知 Token 至少一项减少 15%，另一项不得增加。Token 不完整时不能宣称 Token 收益，已知配对部分仍执行成本上限。实验总账另含提案、预检和所有失败成本，不能仅用胜出的试验成本代表学习投入。

### 生产灰度与独立验收

封存通过只产生 CANARY。参与且未暂停工作台的相同输入适用条件、模型和来源版本的新目标中，稳定抽样约 20% 使用候选，其余形成该候选的同期合格对照；必须保存分组资格，关闭/暂停期间的任意基线目标不能冒充对照。已有目标不换策略、不重复副作用。来源或模型中途变化的混合执行不能继续归因为候选收益。

至少五个可评价候选目标及五个独立匹配对照，并在生产调用/Token 及权威质量上继续满足对应收益通道，才能成为 ACTIVE。最新有效权威观察与历史训练案例分开：取消、重开、未收敛或不可评价的当前状态不能沿用旧正例参与分母。最近十个候选目标中的两个可归因验收失败、硬违规或明确负反馈触发回退；纯冗余读取不是验收失败。全局版本跨工作台监控，拥有者归档不撤销保护。回退只能恢复兼容且未因失败淘汰的安全父版本，否则使用内置基线。三十天样本仍不足停止灰度并保留待复验记录。

AC-EVO-01..06 继续约束声明式边界、隔离、调度、对照、界面及人格管理；新增 AC-EVO-07 约束事实快照、来源组及当前观察，AC-EVO-08 约束生产资格、可归因成本和真实收益闭环。对应测试与人工效果验收见路线图及需求追踪。替身、临时 SQLite、HTTP/renderer 和隔离 E2E 通过属于工程验收；真实供应商协议表现、实际灰度收益及生产回退另验收。本次实现或干跑不得声称已经证明生产收益。

### 设置页的信息范围

当前页面按“当前进展、已采用的方法、学习设置”组织。最近一次真实方法评测与下一步阻塞分开显示；预算消耗只表示成本。方法列表仅展示 ACTIVE/CANARY，拒绝与回退记录继续保留在后台审计中。旧合成批次、合成干跑与评测器标识退出产品页面；旧 API 保持兼容，缺少 v2 DTO 的服务只显示升级提示。

## 历史决策

第一阶段自动演化上下文组织与完成证据检查。Domain 限制策略为预置操作的声明式组合，一批仅改变一个模块；不修改代码、人格、权限、验收器或清图事务。共享证据生成全局基础策略，本台可归因证据生成工作台覆盖层；新目标采用当前有效版本，旧目标固定版本。

基于稳定 Goal/Work/verification 事实记录经验，不将模型自称完成作为客观成功。上一批次得出裁决后，至少十个新观察的可评价任务、其中三个独立任务验收失败才再次启动开发评测（触发口径已于 2026-09-24 修订为跨工作台共享证据池，阈值不变，见文末「修订」）；已裁决批次不再消费其触发证据，基础设施原因结束的批次保留触发以便重试。提案必须指明至少三个开发场景的失败及预期改善，并经复测证实。原始私有内容不进入公开 DTO 或诊断。开发与封存场景独立；评测调用使用真实推理与模拟工具，不能重复生产副作用。

后台扫描只投递持久任务，执行复用 Joi 单槽位，用户输入优先。模型调用先写出站记录并预留独立日额度；出站记录仅供审计，不进入通用出站调度器。额度以关/低/中/高（0/50/150/400 次每日）预设管理，新工作台默认关档并只记录经验，用户明确选择预算后才启动评测。每次调度只执行一次有界调用，额度不足次日继续。瞬时调用失败与崩溃恢复语义一致：保留批次与已完成试验，仅丢弃被中断的尝试，当日停车、次日继续；连续三次失败才放弃批次。调用中断按稳定标识保留审计，未知调用消耗不退款。每天最多一个候选。

合成评测要求三十个不同封存场景、基线与候选各三次，硬违规为零，各场景成功次数不降，总成功率增加至少五个百分点，已知 Token 成本增幅不超过百分之十；Token 缺失时回退比较模型调用数。通过后候选先进入生产 CANARY，至少收集五个候选与五个对照结果且候选失败数不高于对照才晋升 ACTIVE；累计两个验收失败或明确负向反馈会立即拒绝或回退。模型/工具/评测版本不匹配时标记待复验并对新目标使用内置基线。硬违规、成本超限与生产回退冻结该策略于当前模型版本；其余拒绝允许同一策略再提案一次，之后冻结。封存场景集在每次评测器版本升级时轮换，缓解小样本与自适应复用带来的判定噪声。

首版使用十个固定开发场景与三十个固定封存场景。生产经验提供触发条件与版本效果监控，模型从模拟轨迹诊断通用编排缺陷；尚不从生产对话自动生成新评测题。一次完整批次包含开发、候选复测、封存对照共 240 次模拟运行与一次提案，每次模拟最多六次调用，因此最多预留 1441 次调用（不含崩溃恢复重试），可跨多个 UTC 日推进。预算是调用次数上限，不是费用金额。自动化测试使用替身，只证明流程和门禁，真实模型收益需启用后验证。

## 验收映射

### 2026-10-19：执行对照经验与完整成本

评测器版本为 `joi-orchestration-v3`。经验从同一开发场景的基线/候选执行对照确定性提取，包含模型 pin、父策略、评测版本、适用条件、缺陷、声明式改动、数字对照、收益、风险及失效条件；无支持差异时不写。失败或负向对照可以作为避免重犯的经验，封存内容不进入提案。提案只选择与当前失败场景及 pin/父策略/版本匹配的至多四条经验，私有状态保留至多六十条，不增加反思模型调用。

模型调用数包含无效响应重试、失败及中断；恢复同一场景时累计中断成本，未知 Token 保持未知。晋升同时约束实际调用数及已知 Token 的成本增幅；批次账目继续包括提案、开发、验证、封存和失败调用。旧评测版本的缓存不跨版本使用，新目标要求复验；既有目标绑定和灰度/回退边界保持不变。合成评测中的工具不调用压缩或记忆模型，因此这两类调用在该环境中为零，生产延迟收益需要实际使用数据验证。

- AC-EVO-01：严格策略解析、单模块修改、固定强约束；Domain 单元测试。
- AC-EVO-02：经验分型、工作台隔离、版本绑定、零历史重跑；SQLite 集成测试。
- AC-EVO-03：单槽位、预算预留、幂等恢复、用户任务优先；应用与存储测试。
- AC-EVO-04：独立评测、对照轨迹、量化晋升、组合回归、回退；评测与策略测试。
- AC-EVO-05：设置/状态/历史/回滚 API 与工作台详情页签前端，安全 DTO；HTTP 与 renderer 测试。
- AC-EVO-06：移除自主修改人格工具，保留用户管理入口；工具回归测试。

## 修订

### 2026-09-24：触发证据改为跨工作台共享池，并修复证据收敛缺陷

**背景。** 功能上线后一次进化都未启动。运行时取证显示：诊断日志中 175 次任务启动无一属于进化；出站记录中没有任何 `evolution.model` 行；全部工作台状态停在 `collecting`、调用序号为 0。逐层排查后确认调度链路完好（空闲判定、模型源就绪、预算档位均可满足），唯一卡点是证据门槛，而证据收率本身被三处实现缺陷压到 0.9%（112 个目标只产出 1 条可评价证据）。

**修订一：触发口径。** 原决策要求十个可评价任务与三个验收失败按单个工作台统计。全量历史回测表明该口径不可达：使用量分散在二十余个工作台，单个可评价率约 29%、验收失败约占可评价的 15%，要在一台内凑齐三个失败需约七十个实质性目标；修复全部收率缺陷后，仍没有任何一个工作台达到 ev>=5 且 vf>=1。现改为在全部工作台共享的证据池上统计，阈值仍为十与三，且仍只计入该工作台上次裁决之后观察到的证据。策略修订、目标绑定与回滚继续严格按工作台隔离，AC-EVO-02 的隔离语义不变。依据是评测本身跑在固定的合成场景上（十个开发场景与三十个封存场景对所有工作台完全相同），生产证据只回答"编排是否存在缺陷"、不参与评分，因此聚合不会把某个工作台的策略泄漏到另一个工作台。选取执行批次的工作台时优先本地可评价证据最多者，同分按标识排序以保证跨重启确定性。

**修订二：三处证据收敛缺陷。**

- 被撤销（取消 / 忽略）的目标其清图永不停止 ACTIVE。评审清除与自动清除都要求 COMPLETED 终态，trivial 清除又要求目标从未派发过 Work，于是这些目标被证据扫描的"无 ACTIVE 清图"条件永久排除——而失败信号恰恰集中在这条路径上（实测 22 个 ACTIVE 清图全部属于已撤销目标）。现于撤销事务内同步关闭清图，并打上反馈已记录标记以免其成为完成反馈候选；重试与目标续跑本就会把 CLEARED 清图重新置为 ACTIVE，恢复路径不受影响。
- 证据一次写入即冻结。目标在派发第一个 Work 之前被扫到时既无结论也无 Work，会被判为不可评价并永久锁定，其后的验收失败再也无法计入。现允许分类单调升级（不可评价 < 环境失败 < 已取消 < 接受但有缺口 < 已验证 < 验收失败），并新增 `classified_at` 承载幂等判定；`observed_at` 仍是裁决窗口时间戳，只在分类真正升级时前移，因此重复扫描不会重新武装已被裁决消费的触发证据。
- 未声明验收检查（NOT_REQUIRED）被当作缺失结论，连坐否决同一目标内其余已客观验证通过的 Work，实测使 46% 的目标降为不可评价。现 NOT_REQUIRED 不再计入未验证；它同样不计入已验证，因此全部 Work 都未声明检查的目标仍为不可评价，符合"不将模型自称完成作为客观成功"。

**修订三：存量放行边界收紧。** 059 把当时全部存量目标一次性标记为不采样，其中包含仍在途、整个结局都发生在迁移之后的目标。061 按 059 的实际落库时间精确放行这部分（实测 3 个），迁移时已终结的历史目标继续遵循"固定基线且不采样"与零历史重跑。绑定入口同时改为对未绑定真实修订的行做冲突更新，杜绝同类误伤再次发生。

**修订四：可观测性。** 原先所有拒绝路径都是裸返回，"证据不足"与"调度器损坏"在日志上完全无法区分。现补充 `joi.evolution.gate_skipped`（带原因码与池内计数，仅在签名变化时发出以免每两秒刷屏）、`evidence_recorded`、`batch_step_started`、`call_failed` 四类事件；诊断仍为纯观测，不改变任何控制流。`evidence_recorded` 报告的是实际落库的分类而非本次算出的分类——升级被拒绝时两者不同，报告后者会让日志说谎。状态 DTO 同步增加共享池计数（`poolEvaluable`、`poolVerificationFailed`），工作台设置页签因此能直接显示"距启动一轮评测还差多少"，而不是只显示一个已不再对应触发条件的单工作台计数；门槛常量移至 shared 层，使前端与门禁共用同一来源。

**未修订。** 晋升门槛（三十个封存场景、基线与候选各三次、硬违规为零、成功率至少提升五个百分点、调用增幅不超过百分之十）与单批 700 至 1441 次调用的成本保持不变：触发变容易不意味着裁决变宽松。

### 2026-09-24（续）：撤销目标的判定口径与手工干跑入口

**背景。** 修订一之后在真实库副本上复测，闸门仍未打开（池内可评价 4、验收失败 1，门槛 10 与 3）。核算发现撤销路径上还有第二重漏口，而收率修复并不能让证据凭空出现：059 之后只新建了六个目标，其中三个是零 Work 就被忽略的空目标，因此即便修好收率，等待自然累积仍需数周，期间无从验证批次链路本身。

**修订五：撤销目标不再被 CONTINUE 排除。** 证据扫描原本无差别跳过 `disposition = 'CONTINUE'` 的目标，理由是接续目标会承接结局、两行都算会重复计数。但被撤销的目标没有接续可言：它的 outcome 冻结在用户放弃时的取值，排除它等于让"因反复验收失败而放弃"的目标永远不可见。现改为对 `canceled_at` 或 `dismissed_at` 非空的目标放行，活跃接续仍照旧排除。实测放行 3 个存量在途目标。

**修订六：验收失败优先于已撤销。** 分类链原本把 `canceled` 判在 `failed` 之前，于是「撤销且含验收失败」的目标记成 CANCELED、不进可评价池；更棘手的是同一个目标先判后撤会在升级守卫下保住 VERIFICATION_FAILED，先撤后判则只剩 CANCELED，判定结果取决于采样时机。现把 `failed > 0` 提到链首。这是唯一一处越权：`EVIDENCE_RANK` 声明的完整降序（VERIFICATION_FAILED > VERIFIED > ACCEPTED_WITH_GAPS > CANCELED > ENVIRONMENT_FAILED > UNEVALUABLE）在 `VERIFIED` 与 `CANCELED` 交叠处**有意**不取降序——撤销但全部 Work 客观验证通过的目标仍记 CANCELED、不进池（本库三个目标），因为撤销是用户放弃的证据，不是编排成功的证据；`sqlite-evolution-store.ts` 的 rank 表注记已写明这一边界。全量对照：仅提前 `failed` 一格使可评价 33→34、验收失败 4→5，只影响一个目标；改采完整降序则会把 15 个目标从 ENVIRONMENT_FAILED 翻成 VERIFIED，把可评价抬到 49，超出本次决策范围，故未采用。

**修订七：手工干跑入口。** 新增 `POST /api/v1/workbenches/:workbenchId/evolution/dry-run`（write 权限，CSRF 由分发器统一校验）与工作台详情「自主进化」页签的按钮。它在内存中驱动**真实的** `EvolutionService` 跑完整批 DEVELOP、PROPOSE、VALIDATE、EVALUATE 到晋升裁决，但注入确定性替身模型与内存存储：零真实模型调用、不写运行库、不写 outbox、不计用量、不改动真实 revisions/batch/usage，隔离性由 `evolution-dry-run-isolation.test.ts` 在真实数据库上断言。它证明的是编排、游标与门禁协同可用，**不证明**真实策略能带来收益——与文首「自动化测试使用替身，只证明流程和门禁」同调。替身按场景内容而非列表下标推导失败注入，五成余量由 `Math.ceil(0.05 * 场景数 * 3)` 自动维持，健康批次固定 721 步并锁进测试，因此场景作者改动若使链路不再晋升，会以「自检未通过」显式呈现而不是静默跑通。干跑绕不过任何门禁：它用达标证据满足 `#eligible`，阈值仍取自 `shared/evolution.ts` 的同一常量。本入口只补足"证据攒够之前如何验证链路"，不改变触发、晋升与回滚的任何判定。

### 2026-09-28：失败分型、全局候选锁与推进节奏

**背景。** 修订一至七落地后触发门槛已被真实证据跨过，进化开始每天实际投递候选——但随之暴露出投递层的三个缺陷：43 次真实模型调用全部在「响应已计费、处理环节抛错」处失败且原因被空 `catch {}` 吞掉；失败按工作台各自结算，一个 UTC 日内调度器把二十余个工作台逐个起批、逐个失败，每天白烧约二十次调用，实际违反了文首「每天最多一个候选」；候选推进严格一次 handle 一步，在 2 秒调度节拍下预算消耗极慢，批次事实上跑不完。

**修订八：失败分型与全局熔断。** 模型响应不合格式（`evolution_response_invalid`）不再与基础设施故障共用 `call_failed` 语义：它不算连败、不当日停车，rollout 保留原地重试；同一工作台连续两次无效响应即以 `model_response_invalid` 终结批次，且与其它裁决不同、**消费**触发窗口（否则一个不合格的模型源会每天重演付费失败）。跨工作台累计十次连续无效响应触发全局熔断：全部工作台暂停、在途批次终结、无在途批次者仅记原因，恢复仅经 `configure()`。触发窗口的消费只适用于确有裁决的在途批次——对无在途批次的工作台盖章，会把熔断前已积累的证据一并推出窗口，使其在 `configure()` 之后无法按既有积压恢复。诊断新增 `joi.evolution.response_invalid`、`joi.evolution.breaker_tripped`、`joi.evolution.monitor_warning`，`joi.evolution.call_failed` 携带 `errorKind`（经既有脱敏通道，原始 message 不入日志）。用户取消与调度器停滞中断按崩溃恢复处理：保留批次与已完成试验，不计连败、不占当日候选。

**修订九：全局每日一个候选（口径落地）。** 「每天最多一个候选」改为跨工作台执行：读全部 ACTIVE 工作台状态的最大 `lastCandidateDay`，当日已有任何工作台开批，其余工作台即失去候选资格（有在途批次的工作台不受影响，仍可推进）。归档工作台的状态行不参与该判定。用户显式的「立即评测」（`POST …/evolution/run-now`，十五分钟 TTL）绕过证据门槛与该全局锁——被拒绝的批次消费了触发窗口之后，重新攒数周证据不应是唯一的重试路径——但预算、空闲槽位与修订数上限照常生效。已有在途批次时该请求被直接拒绝（`evolution_run_now_invalid`）而不入队：请求只能由开批分支消费，排队会让它越过当前批次的裁决，在同一天再开一个批次。

**修订十：推进节奏与淘汰线。** 一次 handle 允许连续推进至多二十步（每步仍是一次有界调用），并在每步之间重查空闲、预算与取消；墙钟预算两分钟，远低于调度器的十五分钟停滞看门狗，长跑不会被误判为卡死。干跑入口保持一步一调用的旧节奏以维持其步数契约。晋升后的自动回退由「首个监控目标出现验收失败」收紧为「监控窗口内累计两次」，单次失败仅记 `monitor_warning`：一次运气差的失败不应葬送刚通过三十个封存场景对照的候选；目标卡片上的明确负向反馈（手工）仍然立即回退。上批次裁决的三项统计进入状态 DTO（`lastVerdict`），使拒绝的差距可见。

**模型源。** 进化的评测调用在选择模型源时优先「发布即测」或已在真实 Turn 中证明过结构化工具调用的源；无合格源时回退全量池并发 `joi.model_source.tool_proof_fallback`——回退保证可用性不劣于原判定，而修订八的失败分型兜住由此产生的拒答成本。

### 2026-10-10：产品化门禁、分层作用域与可观测性闭环

**失败归因。** `VERIFICATION_FAILED` 不再天然等于策略缺陷。证据同时记录 `context / completion / execution / environment / unknown` 原因；只有 context 与 completion 进入候选触发计数。执行器、环境和未知原因仍保留为审计事实，但不能推动策略改写。存量失败迁移为 unknown，避免升级时误触发。

**分层作用域。** 跨工作台共享证据只能生成 `GLOBAL` 基线修订，不能再落到“本地信号最强”的任意工作台并成为其私有策略。本工作台覆盖层 `WORKBENCH` 必须由该工作台自己的可归因证据达到相同门槛，或由用户在已有全局基线后显式请求评测。运行时按“工作台 ACTIVE 覆盖层 → 全局 ACTIVE 基线 → 内置基线”的顺序组合；目标首次绑定后保持固定版本。

**生产灰度。** 合成封存评测的 promote 裁决只把候选置为 `CANARY`，不再直接 `ACTIVE`。新目标按稳定哈希抽取约 20% 使用候选，其余形成对照；至少五个候选与五个对照目标有客观结果、且候选失败数不高于对照后才晋升。候选累计两个验收失败或收到明确负向反馈立即拒绝。全局候选晋升时取代上一全局基线；工作台候选只影响所属工作台。

**成本与计算。** 封存基线按评测器版本、模型固定版本和父策略缓存；同一基线的后续候选只重跑候选侧。候选出现硬违规、完整场景质量下降，或剩余试验即使全胜也无法达到五个百分点增益时提前终止。成本门禁优先比较 provider 返回的输入加输出 Token；只有 Token 缺失时才回退调用次数代理。

**版本与操作安全。** 当前模型/来源固定版本与已发布策略不一致时，策略进入 `revalidation_required`，对新目标回退内置基线，不再只在内部静默忽略。新工作台每日额度默认 0，用户必须明确选择预算档位。过期 run-now 请求在状态读取或调度时持久清除；三十个修订达到上限时显示 `revision_limit_reached` 并拒绝新的立即评测。

**可观测性。** 每个批次从 DEVELOP 起记录作用域、阶段、开始/结束时间、裁决、调用数、Token 数与可空修订 ID；因此提案前失败也不会消失。`GET /api/v1/evolution` 返回全部工作台的启用数、评测中/灰度中/已生效数、重新验证数、策略证据池和最近批次；工作台状态同时返回当前批次与本地历史。DTO 与诊断只含计数、枚举和稳定标识，不含目标正文、人格、记忆或模型载荷。

### 2026-10-14：单调用契约、失败用量与暂停投影

**调用契约（AC-EVO-01）。** 评测提示词要求每个响应恰好一个受支持的工具调用；读取证据后必须等待下一轮 observation。Anthropic 请求使用 auto tool choice 并禁用并行工具调用，OpenAI Responses/Completions 请求设置 parallel_tool_calls=false；只改变进化请求，保留来源思考设置、固定 pin、原有输出上限与幂等标识。评测器版本为 joi-orchestration-v2，旧策略对新目标显式要求重新验证，旧版本封存基线缓存不用于新评测；已有目标仍保留原绑定。

**失败与成本（AC-EVO-03）。** 模型端口失败只携带固定失败枚举、标准 stopReason、工具调用数量和可空 tokens。供应商错误、内部超时进入基础设施恢复路径；SDK 取消进入取消恢复路径；截断、无工具、多工具与不支持的工具进入原有格式重试路径。真实格式错误仍连续两次终止批次，跨工作台连续十次仍触发全局暂停。响应格式验证之前提取用量，成功或失败都计入已预留的批次调用；成功响应后 pin 校验失败、批次在请求返回前被终止也不得丢失已返回用量。未返回用量、未完成调用经重启恢复时标记未知，不推定零消耗。无效响应的已知用量还保留在当前试验轨迹，参与后续成本比较。

**安全观测与 UI（AC-EVO-05）。** 状态 DTO 返回真实 paused 与最近失败事实，当前和历史批次保留失败分型。诊断增加固定 source/model revision 标识、失败枚举、stopReason 与工具数量，不返回供应商错误原文、模型正文、工具参数或任意工具名称。页面区分“本轮已终止”与“自动进化已暂停”；暂停时禁用立即评测，重新配置预算仍是显式恢复入口。Token 缺失显示未知；旧失败批次中的零值仅在只读投影中标记未知，不回算、不重写历史。

自动化验证使用一次性 SQLite、模型/凭据替身和固定合成响应，不能证明真实供应商已经遵守单调用契约；观察新版失败分型后再决定是否调整模型源。
